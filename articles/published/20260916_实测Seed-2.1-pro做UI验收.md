# 实测 Seed-2.1-pro 做 UI 验收：一套 checklist harness，把检出率从 43% 拉到 70%

> 测评对象：Doubao-Seed-2.1-pro-0915（经 Seed-Evolving API 测试，两者当前版本能力一致）
> 测评场景：UI 设计验收——设计稿 vs 开发实现截图的视觉差异识别、定位标注、修复闭环
> 测评时间：2026-09-16 | 全部数据来自真实 API 调用
> 素材与脚本：[github.com/chankay/ui-review-benchmark](https://github.com/chankay/ui-review-benchmark)

## 一、为什么测这个场景

先交代背景：我做了一轮 UI 设计验收的测评，就是让模型对比设计稿和开发实现的截图，找出视觉差异。选这个场景不是随便挑的，下面会说为什么。

每个前端团队都经历过这种事：设计师对着 Figma 稿说「这个蓝不对，圆角也大了」，开发盯着屏幕找了半天。这种活儿看着简单，其实对模型要求很高——既要能读出色值、间距这种细粒度的视觉信息，又要懂「红涨绿跌」「安全区」这类业务常识，修复完了还得会自己验证。看图说话容易，看图干活难。

我准备了 3 个测试页面（桌面浅色页、深色数据表格、移动端布局），人工埋了 **23 处设计偏差**，每处都标注了类型和 P0/P1/P2 优先级。先看测试素材长什么样：

- **移动端安全区缺失**：底部 Tab 栏紧贴屏幕底边。设计规范里我**故意没写**这条，考验模型的移动端经验知识

## 二、第一轮：整体对比，检出率 43%

用最朴素的方式测：两张截图一起给，让模型自由找茬。

| 页面 | 检出 | 误报 |
|------|------|------|
| 桌面浅色页 | 4/8 | 0 |
| 深色数据表格 | 3/8 | 0 |
| 移动端布局 | 3/7 | 0 |
| **合计** | **10/23 (43%)** | **0** |

第一眼看起来成绩平平。但翻完三份原始输出，有两个行为让我印象很深：

**一是零误报，而且会「存疑不报」。** 深色页的页脚文字实际被我调暗了，模型注意到了这个区域，但没直接报问题，而是在备注里写：「底部辅助文字视觉偏暗疑似截图缩放压缩导致，无充分证据判定为实现偏差」。它宁可漏报也不编造。对比某些模型看图就能编出三个不存在的 bug，这个品质在验收场景里非常值钱：误报会消耗工程师的信任，漏报只是少改一个像素。

**二是主按钮色偏、圆角、badge 缺失这类「块级」偏差全部命中。**

模型到底输出了什么？摘一段它对桌面页的报告原文（完整 JSON 见仓库）：

> **#1 [P0] 色彩偏差 · 主按钮**
> 设计：主按钮背景为品牌主色（深紫色）
> 实现：主按钮背景变为亮蓝色
> 修复建议：将主按钮背景色改回品牌紫色
>
> **#2 [P1] 元素缺失 · 标题右侧状态标签**
> 设计：标题右侧存在「进行中」胶囊状态标签，文字为紫色，底色为浅紫色，圆角 999px
> 实现：标题右侧无任何状态标签，元素完全缺失

每个 issue 都带优先级、设计/实现双侧描述和修复建议，不是一句「颜色不对」就完事。到第三轮 v2 的 checklist 模式，输出更结构化——先给逐区域核对结论，再给 issue 明细。这是它对移动端底部 Tab 栏的核对结论（安全区这条设计规范里我没写，是它自己的经验）：

> **区域：底部 Tab 栏 → 结论：存在偏差**
> **#8 [P0] 安全区问题 · 底部 Tab 栏**
> 设计：Tab 文字底部距屏幕底边有约 34px 全面屏安全留白，无紧贴问题
> 实现：Tab 文字底部距屏幕底边仅约 12px 留白，安全区留白不足
> 修复建议：调整 Tab 栏底部布局，增加不小于 34px 的全面屏安全区留白

最终汇总也有模有样：「页面存在 2 项 P0 阻断级问题、6 项 P1 视觉还原偏差，未达到设计验收标准」——verdict 直接给 fail，不含糊。

## 三、第二轮：checklist harness，检出率 70%

43% 的检出率，问题出在模型还是出在我的用法？我改了一版 harness：不再让模型自由发挥，而是给它一张逐区域核对清单——页头区核字重、每一行数据核颜色和对齐、Tab 栏核底部留白，每个区域必须给出「一致/存在偏差」的结论。

| 页面 | v1 检出 | v2 检出 | v1 tokens | v2 tokens |
|------|---------|---------|-----------|-----------|
| 桌面浅色页 | 4/8 | **5/8** | 10,035 | 7,175 |
| 深色数据表格 | 3/8 | **5/8** | 8,576 | 14,751 |
| 移动端布局 | 3/7 | **6/7** | 7,045 | 11,724 |
| **合计** | **10/23 (43%)** | **16/23 (70%)** | 25,656 | 33,650 |

同一模型、同一素材，只是改了提问方式，检出率从 43% 到 70%，误报保持为零。行密度压缩、分隔线过亮、页脚对比度这些第一轮漏掉的「渐变式偏差」全被 checklist 揪了出来。代价是平均多花 31% 的 token。这买卖划算不划算，取决于你的场景：正式发布前的验收，值得；随手看一眼，没必要。

移动端页面第二轮拿到 6/7：安全区缺失（P0）被抓出来了，而且模型在核对结论里明确写了「Tab 栏距屏幕底部留白不足」。设计规范里没这条，是它自己的移动端经验。

## 四、最有意思的发现：语义色反转悬案

两轮都没抓到那个 P0 级埋点——涨跌语义色反转。第二轮模型给出了一个让我愣了几秒的解释：

> 「设计稿中环比涨跌数据统一使用中性白色，实现与设计一致，无红涨绿跌的语义反转错误」

我回头核对设计稿：+12.4% 是绿色、-3.2% 是红色，清清楚楚。所以问题不是它不懂「涨绿跌红」——它的 checklist 结论里还正确复述了这条规则——而是它把设计稿里的绿色和红色看成了中性白。深色背景、小字号、低饱和度的彩色文字，模型读错了颜色。

说实话，这个发现比「检出率 70%」更让我在意。它说明 harness 工程能解决「没仔细看」，解决不了「看错了」。语义理解、任务规划、工具调用都在进步，但像素级的颜色读数这种地基问题，还没跟上。

## 五、定位标注：框得比想象中准

接着让模型给每个偏差输出边界框坐标（grounding），我用 IoU（交并比）算定位精度，坐标经脚本渲染成标注图：

![深色表格定位标注](shots/page2-dark-data-table-case2-annotated.png)

*深色表格页的自动标注结果：筛选按钮描边丢失（IoU 0.65）、数值列未对齐（0.50）、「接近配额」标签底色丢失（0.53）——框的位置基本准确，这种图可以直接贴进缺陷工单*

![桌面页定位标注](shots/page1-team-management-case2-annotated.png)

*桌面浅色页的标注结果：主按钮色偏/圆角框准了，但状态标签缺失框成了大范围上下文（IoU 偏低）——模型倾向「框大不框小」*

| 页面 | 定位成功 | 平均 IoU |
|------|---------|---------|
| 桌面浅色页 | 5/5 | 0.21 |
| 深色数据表格 | 3/3 | **0.56** |
| 移动端布局 | 5/5 | 0.04* |

先说口径：「定位成功」指模型对某个 issue 输出了非空且落在图片范围内的 bbox，13/13 是这个意义上的全成功，不代表框得准。框得准不准看 IoU（预测框与人工标定真值框的交并比），0.5 以上算基本对位，0.2 以下基本算没对上。

数据表格页表现最好（平均 0.56）：筛选按钮 IoU 0.65、状态标签 0.53、数值列 0.50，框基本都在位置上，这种图直接贴进缺陷工单没问题。浅色页和移动端偏低，看明细发现两个毛病：一是模型倾向框「更大的上下文」（框整张卡片而不是框按钮本身，IoU 被稀释），二是 issue 顺序和清单对不齐，个别框张冠李戴——移动端 0.04 主要是这两个原因叠加，属于「框错了对象」而不是「完全没框」。拿来做「自动标注生成工单」够用了，指望它做精确像素定位还早。

## 六、修复闭环：复检抓到了埋的雷

最后是闭环测试：把验收报告里的修复建议交给 Coding Agent 改代码，改完重新截图，再让模型对照原报告复检。我在修复指令里做了手脚——故意扣下一条建议（内边距压缩没修），看复检能不能发现。

结果比预期好，说三个点：

**修复代码能直接用。** 模型输出的不是「建议调整按钮颜色为品牌色」这种空话，而是 `background-color: #534AB7 !important` 这样的现成 CSS。更意外的是，缺失的「进行中」badge，它直接用内联 SVG 画了一个出来。

![复检输入：修复后的 focus 态截图](shots/page1-team-management-case3-fixed-focus.png)

*复检输入：修复后的页面 focus 态截图。注意输入框的红色描边——这是素材里埋的 focus 态颜色偏差，上轮报告没包含它（静态截图时不呈现），看复检能不能主动发现*

**复检结论是 fail，不是 pass。** 这里有个插曲：本次实验中修复代码的选择器跟页面实际类名不匹配（相当于模拟真实世界的「改了但没改对」），复检时它逐项核对了截图实际表现，6 项全部如实标 unfixed，没有一项是「报告里说修了，那就勾通过」。

**埋的雷抓到了，还顺手抓到一个我没埋的。** 被扣下的内边距问题被它标成「报告外发现」。更有意思的是它还报了一个 regression：「输入框出现设计未定义的红色错误描边，附带淡红色柔光」——那是我在素材里埋的 focus 态颜色偏差，因为静态截图时不呈现，上轮报告根本没包含它，它在复检的新截图里主动揪了出来。

## 七、量化总表

| 指标 | 结果 |
|------|------|
| 差异检出率（checklist harness） | 16/23 (70%)，自由模式 43% |
| 误报率 | 0（两轮、三页面均零误报） |
| 优先级判断 | P0/P1/P2 分级与人工标定基本一致 |
| grounding 定位成功率 | 13/13（表格页平均 IoU 0.56） |
| 修复代码可用性 | 5/5 条可执行，含内联 SVG badge 生成 |
| 复检埋雷检出 | 报告外发现 + 未埋的自露偏差均捕获 |
| 全流程 token 成本 | Case1 两轮 ~59k，Case2 ~21k，Case3 ~15k |
| 单页验收平均耗时 | 60-230s（带深度思考） |

## 八、结论

跑完全程，我最大的感受是：这个模型在「看图干活」这件事上，可靠性明显比覆盖率做得好。零误报、存疑不报、复检不走过场。官方宣传里那些词——「减少编造结果」「产物核验」「行动与反馈一致」——在我这个场景里都验证到了，不是空话。

70% 的检出率配上 checklist harness，放进真实流水线当「第一道自动筛选」是够用的，但复核还离不开人。至于语义色反转那个漏检，就当它给自己留的作业吧：像素级的颜色读数，还是视觉模型要补的地基课。

如果你也要用 VLM 做验收，我的建议就一条：别把它当自由发挥的找茬机器，把它当拿着 checklist 核对的验收员。一张好的核对清单，值 27 个百分点。
