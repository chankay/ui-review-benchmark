# UI 验收 Case 3 — 修复闭环 Prompt（识别→修改→验证）

> 使用方法：Case 1/2 之后执行。分两步：① 把修复建议交给 Coding Agent（Claude Code / TRAE / Codex）改代码；② 复检——把修复后的新截图再发给模型验收。
> 文章高潮点：第一轮修复故意只要求修 6/8 处，复检时看模型能否发现漏网之鱼（产物核验能力）。

---

## Step 1 — 修复指令（发给 Coding Agent）

以下是一份 UI 验收报告，请根据其中的修改建议修改当前项目的样式代码。

【验收报告】
{粘贴 Case 1 的 JSON 输出}

【要求】
- 按 P0 → P1 → P2 的顺序逐项修复
- 每修复一项，在代码注释中标注 `<!-- fix: issue#N -->`
- 修改完成后输出：修复清单（issue_id + 修改的文件/行）
- 如果某项建议你认为不合理或与现有设计系统冲突，不要修改，单独列出并说明理由

> 埋点技巧：文章里第一次运行时手动删掉报告中 2 条 P2 建议（如 #6 描边丢失、#8 对比度），模拟"修复不完整"的场景，为复检埋雷。

## Step 2 — 复检指令（发给被测 VLM）

这是修复后的页面截图。请对照以下验收报告（上轮输出）逐项复核：

【上轮验收报告】
{粘贴 Case 1 的 JSON 输出}

请输出复核结果 JSON：

```json
{
  "recheck_summary": "总体结论：是否全部修复",
  "verdict": "pass 或 fail",
  "fixed": [
    { "issue_id": 1, "verified": true, "evidence": "截图中观察到的修复后表现" }
  ],
  "unfixed": [
    { "issue_id": 6, "verified": false, "evidence": "截图中仍然存在的问题表现", "is_new_regression": false }
  ],
  "regressions": [
    { "description": "修复过程中引入的新偏差（如有）", "severity": "P0 | P1 | P2" }
  ]
}
```

【要求】
- 逐项核对，不得凭报告说 fixed 就认定 fixed——必须以截图实际表现为准
- 特别注意：报告未提及但截图上新出现的问题，记入 regressions
- 如果所有问题确实全部修复，verdict 才是 pass

## 评分口径（文章量化表用）

| 指标 | 计算方式 |
|------|---------|
| 复检检出率 | unfixed 中正确识别的比例（埋雷 2 条，满分 2） |
| 误通过率 | 把 unfixed 误判为 fixed 的比例 |
| 回归检出 | 是否发现 Step 1 修复引入的新偏差（可选埋点） |
| 闭环成功率 | 复检 pass 后整条链路（识别→修复→验证）自动完成的比例 |
| Token 成本 | 三步全流程的输入+输出 token 总量，跨模型对比 |
